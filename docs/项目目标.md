# 鸿蒙 PC 内存错峰回收项目目标

更新日期：2026-10-14，香港时间。

本项目面向鸿蒙 PC 多应用并发时的内存压力问题，建设可验证的用户态内存错峰回收服务及配套测试框架。在负载上升前，从符合条件的后台应用回收冷内存，为即将发生的内存需求准备空间，降低启动失败、内核 OOM 查杀和低内存弹窗，并控制后台应用恢复代价与服务开销。

当前约 32GiB 样机用于机制验证和工程联调。正式验收以已有项目说明中的 16GiB 设备要求、固定工作负载和指标口径为准；新增的 8GiB 近似模拟属于实验环境探索。

## 交付目标

| 交付项 | 预期能力 | 完成条件 |
|---|---|---|
| 常驻回收服务 | 采集内存状态，根据有效的未来负载信息选择后台供体，执行受预算约束的提前回收 | 目标身份、前后台状态、额度和执行结果可核查，异常时停止后续动作，原服务可恢复 |
| 场景测试框架 | 执行应用切换、内存升峰、异常触发、采集、审计和版本比较 | 相同配置能重复执行，结果能追溯到原始日志、截图和进程身份 |
| 真实应用供体接入 | 将浏览器等真实应用的完整进程组纳入供体判断 | 隔离进程 UID、PID、启动时间、组成员关系及窗口状态一致，前台和可见应用得到保护 |
| 实验和交付资料 | 提供源码、配置、构建说明、运行说明、结果及限制 | 代码与本地采集资产边界明确，能够复核实验条件及有效性 |

## 正式性能目标

下列指标沿用[根目录运行说明](../README.md)和[常驻服务说明](../常驻服务代码/memshift_cpp/memshift_cpp/README_zh.md)。这些是待验证的目标，不是当前收益结论。

| 场景 | 主指标 | 目标 | 比较条件 |
|---|---|---|---|
| 场景 1 应用切换和复用 | 固定重访窗口内目标应用完整进程家族的复用缺页次数均值 | 下降至少 20%，挑战目标为 30% | 基线与优化版各 10 个有效独立轮次；同设备、容量、应用身份及工作负载；生命周期和计数覆盖完整 |
| 场景 2 内存错峰调度 | 启动失败、确认的内核 OOM、可见低内存弹窗三类事件合计均值 | 下降至少 30% | 16GiB 实机或厂商认可的真实降容；先校准、完成三类齐全且分类合计至少 100 的资格集并冻结；正式基线与优化版各 3 个有效独立轮次，按 README 执行完整门槛 |

下降比例按 `(基线均值 − 优化版均值) / 基线均值 × 100%` 计算。基线为零时不计算下降百分比，应重新评估场景是否能验证目标。

基础版曾使用 10% 作为阶段性实验目标，近期合成场景使用过 15% 内部机制目标；二者不替代上述正式指标。场景 3、场景 4及真实浏览器供体诊断用于探索机制和完善采集，只有满足相应正式条件后才能进入验收比较。

## 回收策略目标

1. 在可验证的未来内存需求发生前预留空间，明确区分“已知未来事件”与真实预测器输出。先验证机制，再验证实际可获得输入下的效果。
2. 根据后台状态、冷页容量、系统缺口、保留量和 swap 余量选择供体。真实浏览器按完整进程组核查，不能把所有渲染进程都视为浏览器主进程 UID。
3. 匿名页、文件页和文件写回分别记账。计划量、提交量、驻留下降、压缩量、换出量和实际物理空闲增量分别报告，避免将请求成功等同于释放成功。
4. 保留全局与每应用预算、单次上限、冷却、退避、身份复核及前台保护。出现未知身份、过期证据或采集缺口时停止依赖该证据的动作。
5. 同时测量目标应用成功率、时延、供体恢复代价、服务 CPU/RSS 和写盘开销，避免仅凭空闲内存增加判断优化有效。

## 证据和比较要求

- 内核 OOM 必须有真实内核记录，并尽可能关联精确的 PID、UID、启动时间和退出证据；渲染进程退出、普通超时或策略杀单独统计。
- 弹窗必须有测量窗口内实际可见的 UI 证据；请求、通知回调或被遮挡的窗口不能直接计为可见弹窗。
- 同一事故可以进入多个有独立依据的事件类别，去重事故数另报，不能用事故数替换分类事件门槛。
- A/B 必须使用相同负载、目标、计数规则和约束；采集缺口和约束失效不得用零事件替代。派生审计与原始结果并列保存，不能覆盖原始结论。
- 原服务恢复、目标应用清理和控制状态回读属于实验闭环。历史 PID 和窗口身份不能复用于下一轮。

## 内存容量实验目标

正式 16GiB 验收需要真实目标设备，或厂商认可且实测容量符合要求的降容方式；修改配置中的 `dram_gib` 不改变物理容量。

针对当前样机，可探索“固定锁页占用后减少其他工作负载可用容量”的近似实验。2026-10-14 的只读检查显示系统 `MemTotal` 约 31.17GiB，若按总容量扣除计算，希望系统和其他应用共享约 8GiB，预占量应约为 23.17GiB；预占 24GiB 则剩约 7.17GiB。这些数字表示容量差，并非剩余空闲内存。

该实验先验证小规模分配、实际触碰、锁页、驻留核查和退出释放，再分档增加占用量。当前仅确认 root 和无限制锁页额度，尚未验证 `mlock()` 实际行为或大规模锁页成功。HongMeng 内核的启动限容方法仍待厂商接口确认；系统总内存感知及 50GiB swap 配置也不会因预占内存自动变成真实 8GiB 设备的状态。

## 下一阶段完成条件

| 阶段 | 完成条件 |
|---|---|
| 真实供体机制验证 | 单次回收链路能够重复完成，供体身份和保护检查一致，原服务准确恢复 |
| 浏览器对照实验准备 | 原始内核采集与规定门控覆盖全窗口，固定页面负载稳定，选定能形成有效基线的压力档位 |
| 真实供体收益验证 | 完成相同条件下的有效 A/B 重复实验，报告异常事件、供体恢复代价和资源开销 |
| 正式验收 | 在符合容量要求的目标设备重新校准、冻结并完成规定轮次和指标比较 |
