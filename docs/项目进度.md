# 鸿蒙 PC 内存错峰回收项目进度

更新日期：2026-10-14，香港时间。

项目已具备场景执行、内存采集、常驻回收、进程身份校验、实验审计及服务恢复能力。在约 32GiB 样机的已知未来合成负载下，三对内部 A/B 观察到异常事件合计从 44 次降至 0 次，支持继续推进错峰回收机制。当前重点是将供体切换到真实浏览器，并解决高压采集和门控覆盖问题；正式 16GiB 验收与真实应用稳定收益仍待完成。

## 已有结果

### 场景 1 和场景 2 预验证

场景 1 的完整负载轮已记录 48GiB 自有应用触碰与 12GiB 压力释放。最近汇总的重访端点缺页诊断为 14,873 次，但全序列 trace 和短命子进程覆盖仍不完整，不能将该数字用于正式 20% 改善比较。

场景 2 的 32GiB 固定资格集通过独立审计后，分类事件为 137 次、去重事故为 74 次，生成了 `prevalidation_32gb` 冻结文件。原始结果中的计数和不完整标记仍保留，使用时须同时提供对应审计；该冻结不适用于正式 16GiB 验收。详见[预验证记录](prevalidation_20261006.md)。

### 合成场景三对内部对照

2026-10-12 的三对实验使用同一启动周期和冻结负载。A 使用相同候选服务进行采样，关闭主动回收；B 使用提前 90 秒的已知未来事件执行回收。

| 观察指标 | A 累计 | B 累计 |
|---|---:|---:|
| 确认的内核 OOM | 41 | 0 |
| 实际启动或升峰失败 | 0 | 0 |
| 可见系统原生低内存弹窗出现次数 | 3 | 0 |
| 三类观察合计 | 44 | 0 |

按观察合计下降 100%，超过该轮 15% 内部机制目标。A 的 OOM 包含 24 次场景应用和 17 次场景外进程，因此此处为系统范围观察合计；两组目标应用均成功，不能将结果解释为改善了启动失败。

该结果限于约 32GiB 样机、自有供体及完全已知未来事件。原始 runner 六臂因 `trace_start_failed` 标为 invalid，结果来自并列保存的独立内核审计和 WMS/截图观察；第三对 B 存在两次弹窗元数据 unknown。该内部对照不能直接替代正式验收，也不能据此保证所有短暂弹窗均不存在。完整口径见[三对内部对照报告](../results/scene4_measurement_closure_20261012/three_pair_combined_report.md)。

### 日常服务联调与真实浏览器供体

2026-10-12 的日常版本接入记录显示：候选服务在保留原四办公应用、小额度和关闭实验性 oracle/磁盘模式的配置下完成 90 秒空闲试运行，未发生主动回收动作，保留了原版本回退材料。这证明服务切换和空闲运行链路可用，不能证明办公负载已有异常收益。见[日常服务接入回执](../results/daily_lead_rollout_20261012_2200/rollout_report.md)。

2026-10-13 的浏览器单次链路诊断已观察到一次确认的匿名回收写入，随后恢复原服务，SELinux 保持 Enforcing。浏览器供体采用六个最小化窗口、每窗口三个离线页面，并核查主进程、隔离渲染进程的真实 UID、PID、启动时间、cgroup 成员和窗口状态。该单次结果证明链路连通，不代表稳定收益。见[单次诊断记录](../results/browser_donor_integration_20261013/reclaim_diag_01/diagnostic.json)和[供体工具说明](../tools/browser_donor/README.md)。

## 真实浏览器实验的主要问题

当前压力档位名称表示实验目标负载，不表示样机物理容量。以下均为基线或诊断记录，尚未组成有效的真实供体 A/B 比较。

| 档位 | 已有观察 | 有效性与问题 |
|---|---|---|
| 8GiB | A03 原生控制器完成，内核窗口观察到 0 次 OOM | 约 T+453 秒只读门控状态丢失，完整窗口内磁盘换出排除条件未验证，不能进入比较 |
| 10GiB | 中断前记录 14 次内核 OOM 动作 | 采集窗口不完整，设备发生启动周期变化，重启回读为 `HM_PANIC`；不能据此单独确定 panic 根因 |
| 9GiB | 原始记录解析出 9 条 victim 签名 | 采集器发生 EPIPE/read_error，门控和结束窗口不完整，不能作为完整计数基线 |
| 8.5GiB | A02 原始内核采集被标为有效，观察到 0 次 OOM | 门控仅覆盖 1190/1862 次预期轮询，整体 `valid_for_oom_comparison=false` |
| 8.75GiB | 独立校准运行器、指纹和前置校验已编写 | 当前没有可用于比较的完整设备结果；有界单次重新关闭门控辅助工具尚未接成端到端 A/B 运行器 |

8GiB 和 8.5GiB 零 OOM 的观察不能证明优化有效；真实浏览器在压力期间会自行减少匿名驻留、压缩、换出或退出部分进程，必须与内核 OOM 分开分析。近期门控候选已在设备通过时钟、解析器和配置三项自检，但自检没有写控制节点、切换服务或执行压力负载，不能代表完整门控实验通过。

## 内存限容确认

2026-10-14 只读检查确认，样机运行 `HongMeng Kernel 1.13.0 aarch64`，标称 32GiB，系统 `MemTotal` 约 31.17GiB，检查时 `MemAvailable` 约 22.42GiB，swap 总容量为 50GiB。root 权限和锁页软硬额度无限制均已确认。

目前未找到已确认可用的启动限容参数，也未发现标准 `/sys/devices/system/memory` 热移除接口或 GRUB 配置。Linux 的 `mem=8G` 不能直接视为该鸿蒙内核支持的操作。锁页接口和大规模分配尚未做运行测试；此次未修改设备配置、未重启、未施加大内存负载。见[能力检查摘要](../results/memory_limit_capability_20261014_120143/summary.json)。
